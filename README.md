# eska: 1C Explorer

Расширение VS Code для навигации по метаданным 1С в формате Designer XML.
Работает через установленный `eska ide --stdio`; проект определяется по
обязательному `eska.toml`.

Реализованы подключение (T76), дерево метаданных (T77), поиск (T78) фильтр (T79) и иконки (T80): проекты
и участники workspace, вложенные объекты, первая группа «Модули», открытие XML/BSL,
обновление изменённых ветвей, переход к результатам поиска и фильтр пустых разделов.
Упаковка и итоговая приёмка — следующая задача T81. Публикации в Marketplace пока нет, publisher ещё не выбран.

В Explorer нет собственных BSL/SDBL languages, grammar, debugger, форматтера и
диагностики BSL. Расширение не требует bsl-analyzer и не меняет настройки других
расширений, `launch.json` или ассоциации файлов.

## Подключение

1. Откройте папку с `eska.toml` в доверенной рабочей области.
2. Установите совместимый backend eska отдельно. При необходимости укажите
   абсолютный путь в `eska.explorer.executable`; по умолчанию используется `eska`
   из PATH. Аргументы командной строки в этой настройке не поддерживаются.
3. Раскройте представление **eska: 1C Explorer** в проводнике VS Code.

Команды **eska Explorer** позволяют выбрать проект, перезапустить или отключить
подключение и открыть журнал. Из нескольких независимых папок VS Code выбирается
одна. Если это корень workspace eska, backend открывает его участников по
существующим правилам `eska.toml`. При переключении папки старый процесс сначала
завершается. Повторные попытки после ошибки выполняются по команде пользователя.

Если manifest отсутствует, показывается [инструкция настройки](docs/setup.ru.md).
Расширение не запускает `eska init` и не устанавливает executable автоматически.
Изменение настройки пути отключает прежнее подключение; затем используйте команду
перезапуска. Изменение `eska.toml` автоматически переподключает текущий контекст.

## Дерево и исходники

Порядок и подписи групп задаёт backend по типу проекта: конфигурация,
расширение, внешний отчёт или обработка. Ветки загружаются при раскрытии;
пустые разделы корня скрыты по умолчанию.

У корня каждой конфигурации и расширения есть кнопка фильтра: **Показывать пустые
группы корня / Скрывать пустые группы корня**. Скрываются только подтверждённо
пустые разделы корня; незагруженные, ошибочные и вложенные группы остаются.
«Общие» видно, если заполнена хотя бы одна вложенная группа. Внешние отчёты и
обработки не фильтруются, кнопки у них нет. Группу модулей без существующих BSL
backend не создаёт независимо от фильтра, в том числе при наличии только `.bin`.

Настройка **Eska › Explorer: Hide Empty Root Groups**
(`eska.explorer.hideEmptyRootGroups`, по умолчанию `true`) задаёт исходный режим.
Приоритет: явный выбор проекта → настройка папки → workspace → user → умолчание.
Выбор кнопкой хранится отдельно для каждого проекта в `workspaceState` VS Code
и переживает перезапуск IDE; он не записывается в `eska.toml` или исходники.
Контекстное действие **Использовать фильтр по умолчанию** снимает выбор проекта
и возвращает применение настройки, включая её последующие изменения.

Переключение использует готовые состояния backend и кеш ветвей, не переиндексирует
проект и не разбирает XML повторно. Раскрытие сохраняется; если выбранная группа
или её родитель скрывается, выделяется корень проекта без переноса фокуса из
редактора. Добавление/удаление последнего объекта меняет видимость раздела после
обычного обновления файлов.

«Модули» расположены первыми и изначально раскрыты. После ручного сворачивания
группа остаётся свёрнутой при обновлении ветки в текущем сеансе расширения.
Показываются только существующие BSL; двоичные модули без BSL скрыты.
Общие модули показаны без вложенной группы «Модули»: нажатие на имя сразу
открывает BSL, контекстное меню **Открыть XML** — описание объекта. Если BSL
отсутствует (например, есть только `.bin`), объект остаётся доступен для открытия
XML; попытка открыть код сообщает об отсутствии исходника. Редактор свойств
пока не реализован.

Выбор остальных модулей открывает BSL, объекта или вложенного элемента — его XML с выделением
свойства «Имя». Файл и координаты предоставляет backend. До открытия BSL его
содержимое для дерева не читается. Несохранённый XML не перезаписывается:
для точного перехода требуется сохранить правки и обновить ветку.

Изменения файлов передаются backend пакетами с интервалом 100 мс; изменяются
только затронутые ветви, сохраняются выделение и раскрытие соседних объектов.
Повреждённый XML показывает локальную ошибку; после исправления ветка доступна
снова. Команда **Обновить метаданные** обновляет все проекты, действие у узла —
его ветку. Ручное обновление также восстанавливает дерево после пропущенных
системой событий или исключения исходников из наблюдения настройками VS Code.
Изменения manifest требуют нового подключения и могут сбросить текущее выделение.

Для дерева используются нативные элементы: клавиатурная навигация,
масштаб и темы обслуживаются VS Code. Все 67 видов метаданных, группы и роли
модулей используют локальные SVG согласованного стиля; служебные действия и
ошибки — нативные ThemeIcon. Есть цветные и контрастные варианты для светлой и
тёмной темы. Смена темы перерисовывает иконки без переподключения или сброса кеша.
Прорези прозрачны, поэтому выбранная строка не получает фоновых заплаток.

Тип объекта передаёт backend в поле `Node.metadataKind` (дополнение IDE API 1.0).
Для полного набора значков объектов нужен обновлённый backend с этим полем;
при его отсутствии или неизвестном типе показывается универсальный значок.
Группы и роли определяются по уже существующим типизированным полям протокола.
[Таблица соответствий и происхождение SVG](docs/icons.md).

Язык названий групп и ролей модулей задаётся в **Eska › Explorer: Tree Language**
(`eska.explorer.treeLanguage`): **Авто / Русский / English** (`auto`, `ru-RU`,
`en-US`). По умолчанию «Авто» следует языку VS Code: русский для русской IDE,
английский для остальных языков. Изменение применяется сразу, без перезапуска
backend и повторного чтения метаданных; выделение и раскрытие сохраняются.
Имена объектов из конфигурации не переводятся, язык команд и ошибок остаётся
языком IDE.

## Поиск

Кнопка с лупой и команда **eska Explorer: Поиск метаданных** (`Search metadata`)
открывают стандартный Quick Pick. Введите часть имени или синонима объекта либо
вложенного элемента; стрелки выбирают результат, Enter раскрывает его путь и
выделяет узел в дереве, Escape закрывает поиск. Выдача содержит имя, локализованный
вид метаданных, проект и путь владельца из backend. Вид метаданных следует
настройке `eska.explorer.treeLanguage`: например,
«Общий модуль» / «Common module». Переключение обновляет открытую выдачу без
повторного поиска. Идентификаторы пути клиент не разбирает; одинаковые имена
и ID разных проектов не объединяются.

Поиск охватывает нераскрытые ветки и синонимы всех языков. Он нечувствителен к
регистру, ищет буквальную подстроку, без нечёткого сопоставления и объединения
«ё» с «е». Виртуальные группы и модули не входят в выдачу. Состав совпадений
определяет backend; стандартный Quick Pick может дополнительно сортировать
видимые строки по введённому тексту.

При первом открытии поиска eska начинает фоновую индексацию. До её завершения
показываются частичные совпадения и счётчики; ошибки отдельных XML отмечают индекс
как неполный. Сообщение «Совпадений нет» появляется только для готового индекса.
Готовый индекс повторно используется, после изменения исходников обновляется.
На каждый проект выводится не более 50 совпадений; при усечении нужно уточнить
запрос. Ввод объединяется с задержкой 250 мс, обновления прогресса — 500 мс.

Предыдущий запрос отменяется через IDE-протокол; поздний ответ не заменяет новую
выдачу. При выборе backend заново проверяет существование объекта и возвращает
путь: загружаются только необходимые ветви. Удалённый результат показывает ошибку.
Кнопка обновления повторяет поиск. Закрытие окна отменяет запросы, но уже начатый
индекс достраивается в фоне; отключение проекта закрывает поиск и backend.

## Диагностика подключения

Команда **eska Explorer: Показать журнал подключения** открывает журнал VS Code.
В нём записываются время, PID, путь к backend, его версия и параметры проекта;
для каждого запроса — ID, метод, поколение, размер очереди и время выполнения.
Ошибки содержат категорию backend, причину и адрес исходника, если они известны.
Текст XML/BSL и полные тела запросов/ответов в диагностические события не попадают.
Пакеты событий файлов содержат количество путей и ограниченный образец.

`request_timeout` показывает, какой запрос не завершился, сколько он ожидал,
когда последний раз приходили данные и получен ли неполный ответ. Если после
него стоит `process_signal` с причиной `timeout`, процесс завершило расширение.
`process_closed` показывает код выхода, сигнал и инициатора остановки. Обычное
отключение не записывается как авария.

Сообщения stderr сохраняются в пределах первых 16 КБ и последних 16 КБ:
при превышении лимита поздняя причина завершения остаётся в `stderr_tail`.
Для разбора сбоя нужны события от `connection_connect` до `process_closed`.
Тайм-ауты не увеличены: журнал помогает отличить медленную операцию/очередь от
аварийного выхода, но сам по себе не устраняет причину задержки.

## Где работает backend

Минимальная версия VS Code API — **1.109.0**. Расширение объявлено как `workspace`:
в Remote SSH, WSL и Dev Containers требуется установить eska на соответствующей
машине/в контейнере. Настройка пути допускает отдельные значения для этих сред.
Виртуальные workspace и web extension host без Node не поддерживаются;
в недоверенной рабочей области расширение отключено.

UI лишь отображает результаты backend: парсер XML, каталог типов и кеш остаются
в eska. При открытии включён дисковый кеш backend. Источник никогда не сканируется
вторым индексатором на TypeScript.

## Разработка

Зависимости закреплены в `bun.lock`: TypeScript 7.0.2, API VS Code 1.109.0,
типы Node 22.20.3. Инструменты проверены 2026-09-18; Bun — 1.4.2.
Production-код не имеет npm runtime-зависимостей и исполняется в Node extension
host VS Code. Bun используется для инструментов проекта.

```bash
bun install --frozen-lockfile --ignore-scripts
bun run --bun check
bun run --bun compile
bun test
```

Для проверки именно Node runtime после компиляции:

```bash
node --test test/*.test.mjs
```

Интеграционная проверка использует существующий бинарник CLI и создаёт только
собственный временный каталог внутри соседнего `eska-playground`:

```bash
ESKA_TEST_BINARY="$(realpath ../eska/target/debug/eska)" \
ESKA_TEST_ROOT="$(realpath ../eska-playground)" \
node --test test/integration.test.mjs test/tree.test.mjs test/search.test.mjs
```

Без `ESKA_TEST_BINARY` тесты реального backend пропускаются; unit/process tests остаются
обязательными. Сборка/выгрузка 1С не запускается. Для ручного запуска после
компиляции: `code --extensionDevelopmentPath="$PWD" <папка-проекта>`.

Для автоматической проверки нативного дерева в установленном VS Code/VSCodium
нужен рабочий графический сеанс. Тест создаёт отдельный профиль и проект в
playground, проверяет XML/BSL, клавиатурное сворачивание, сохранение выделения,
внешние изменения, повреждение/восстановление XML и смену manifest:

```bash
ESKA_TEST_BINARY="$(realpath ../eska/target/debug/eska)" \
VSCODE_EXECUTABLE=codium bun run test:host
```

Отдельный нативный сценарий фильтра (без команд клавиатурного фокуса):

```bash
ESKA_TEST_BINARY="$(realpath ../eska/target/debug/eska)" \
VSCODE_EXECUTABLE=codium node test/run-host.mjs test/filter-host.cjs
```

Сценарий иконок проверяет четыре темы, вложенные элементы и уровни масштаба:

```bash
ESKA_TEST_BINARY="$(realpath ../eska/target/debug/eska)" \
VSCODE_EXECUTABLE=codium node test/run-host.mjs test/icons-host.cjs
```

Для VS Code используйте `VSCODE_EXECUTABLE=code`. Electron не скачивается.
В обычном CI этот графический тест не запускается; нужен установленный editor
и совместимый backend. Доступ к контроллеру дерева экспортируется только в
режиме тестового Extension Host и не является API расширения.

Проверки T76/T77: Linux, Bun 1.4.2 и Node 22.23.1; реальные stdio-запросы к eska
проверяют четыре типа проектов, workspace из двух участников, ошибки manifest,
перезапуск и отсутствие оставшихся процессов. Smoke-test в Extension Host
VSCodium 1.109.5 (Node 22.21.1) подтвердил активацию, подключение, перезапуск
и отключение с проверкой дочерних процессов. Windows, macOS и Remote пока
не проверены в реальной среде; полная матрица приёмки относится к T81.

## Устройство

- `protocol.ts`, `framing.ts`: валидация wire-ответов и Content-Length framing.
- `process.ts`: bounded queues, таймауты, stdout/stderr и завершение своего child.
- `connection.ts`: handshake, один discovery context, защита от устаревших ответов.
- `tree.ts`: ленивые ветви, стабильные идентификаторы и проверка поколений/событий.
- `icons.ts`, `resources/icons`: таблица видов/ролей и локальные SVG четырёх тем.
- `filter.ts`: фильтрация по состояниям backend и сохранение выбора каждого проекта.
- `search.ts`, `search-view.ts`: отменяемый поиск, прогресс индекса, проверяемый reveal и Quick Pick.
- `source.ts`: source mapping, проверка существования/границ пути, UTF-8 → UTF-16 координаты.
- `watch.ts`: ограниченные пакеты файловых событий и наблюдение за manifest.
- `extension.ts`: нативное представление, выбор папки, команды и сообщения RU/EN.

Контракт находится в соседнем репозитории `eska`: `docs/ide-protocol.md`.
Решения API опираются на официальные [Extension Host](https://code.visualstudio.com/api/advanced-topics/extension-host),
[Remote Development](https://code.visualstudio.com/api/advanced-topics/remote-extensions)
и [Workspace Trust](https://code.visualstudio.com/api/extension-guides/workspace-trust).
