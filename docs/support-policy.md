# Правила поддержки 1С

ESKA читает правила в Rust-backend и добавляет ограничения конкретным исходникам.
Режим файла одинаков при открытии из ESKA, обычного Explorer, Quick Open, поиска
или восстановленной вкладки. Подключение начинается без раскрытия панели ESKA.
До завершения полного анализа и применения read-only вместо дерева показывается
«Проверка правил поддержки 1С…» со спиннером. После готовности дерево остаётся ленивым,
но статусы поддержки уже загружены. Открытые текстовые редакторы продолжают работать.
Папки VS Code workspace используют независимые backend-сессии; UUID разных
проектов не смешиваются.

| Справа от объекта | Значение |
|---|---|
| 🔒 | Изменения запрещены правилами поддержки |
| S | Редактирование с сохранением поддержки |
| Без значка поддержки | Собственный объект либо объект снят с поддержки |
| ? | Статус неизвестен, данные обновляются или backend несовместим |

Тип метаданных остаётся слева. Значки справа видны постоянно и ничего не
разблокируют. Tooltip объясняет состояние; Git сохраняет цвет и своё обозначение
в совместном tooltip. У групп остаётся Git-индикатор, без наследования замка
от одного запрещённого объекта.
При прокрутке готовый значок поддержки возвращается сразу из памяти, не ожидая
очереди запросов Git. Цвет и пояснение Git добавляются отдельным обновлением.

Для обычного Explorer используются реальные файловые URI. Если XML содержит
объекты с разными разрешениями, весь XML открывается read-only; tooltip сообщает
о совместном хранении. В дереве разрешённый объект сохраняет свой собственный
статус. Отдельный разрешённый модуль остаётся редактируемым.

## Механизм read-only

Используется `files.readonlyInclude` в области Workspace с точными абсолютными
путями; в больших проектах они объединяются в ограниченные группы альтернатив
без wildcard-запрета на соседние файлы. ESKA сохраняет журнал принадлежащих ей ключей в workspaceState, учитывает
существующие правила и удаляет только собственные неизменённые ключи при
пересчёте, отключении подключения и деактивации. Другие пользовательские правила,
включая добровольную блокировку `.bsl` и `.os`, сохраняются. Изменения настроек,
пришедшие одновременно с записью ESKA, учитываются отдельно.

Файлы не переводятся на виртуальные URI, права ОС не меняются. ESKA никогда не
вызывает `setActiveEditorWriteableInSession` и не сбрасывает сессионные блокировки.
Если документ уже изменён, его текст, вкладка и позиция сохраняются; при новом
запрете показывается предупреждение. Автоматического сохранения или отката нет.

**Это снимаемый штатный read-only.** Команда
`workbench.action.files.setActiveEditorWriteableInSession` имеет приоритет над
настройками файла. Её действие сохраняется при последующих изменениях настроек
read-only в этой сессии. Пользовательские `files.readonlyExclude` тоже могут
исключить файл из действия include. Значок показывает правило поддержки,
а не доказательство неснимаемой блокировки редактора.

Сохранённые настройки могут остаться после аварийного завершения Extension Host;
журнал используется при следующем подключении/деактивации. Это отличается от
нормального отключения, для которого выполняется очистка. Удаление расширения
после аварии без повторного запуска не даёт ему выполнить очистку; принадлежащие
ему точные пути тогда нужно удалить из `files.readonlyInclude` вручную.

## Обновление и неизвестное состояние

Изменения XML, правил поддержки и переключение веток через файловые события,
ручное обновление и переподключение приводят к пересчёту. Ответы прежних сессий
или поколений отбрасываются. Во время полного пересчёта дерево скрыто прелоадером.
При ошибке запроса показывается сообщение с повторной проверкой через обновление.
Завершившийся анализ с нечитаемыми правилами показывает диагностические `?`.
Первые подтверждённые ограничения применяются до завершения обхода, остальные —
перед показом дерева; пока конкретный файл не проверен, его защита не гарантируется.

Backend хранит разобранный файл правил по SHA-256 содержимого. Одинаковая перезапись
`ParentConfigurations.bin` не запускает повторную проверку. Изменение, удаление
и восстановление файла запускают её автоматически; ручное обновление проверяет
актуальность содержимого. Изменения XML при выгрузке отдельно обновляют принадлежность
файлов. Обычное сохранение уже известного BSL не запускает анализ поддержки и прелоадер.

Невозможность прочитать правила не считается снятием поддержки. Диагностика
показывается в tooltip. Если поддержки ранее не удавалось подтвердить, отсутствие
`ParentConfigurations.bin` отображается как неизвестное состояние без добавочного
запрета. Повреждение сведений или исчезновение ранее прочитанных правил вызывает
консервативный read-only распознанных исходников. При недоступном дескрипторе
ранее установленные ограничения его файлов не удаляются молча.

Backend без `supportPolicy` остаётся пригоден для навигации; защита не объявляется
работающей. Правила поддержки, UUID и исходники открытием проекта не изменяются.
Корректность произвольных правок BSL/XML эта функция не проверяет.

## Фактические проверки

Linux, VSCodium 1.109.5: обычные файловые URI, открытие до раскрытия дерева,
смешанный XML, разрешённый отдельный модуль, пользовательские BSL/OS-блокировки,
грязный документ, переключение веток, повреждение правил, сессионная
разблокировка, очистка настроек и две папки workspace с одинаковыми UUID,
удаление выбранной папки и сохранение защиты при обрыве второй backend-сессии.

Скриншоты настоящего дерева: [тёмная](measurements/support-policy/support-dark.png),
[светлая](measurements/support-policy/support-light.png),
[контрастная](measurements/support-policy/support-contrast.png),
[светлая контрастная](measurements/support-policy/support-contrast-light.png).
На них Locked имеет одновременно правило поддержки и Git M; tooltip проверен
тестом, Git-цвет сохранён. Own и Removed не получают ограничивающего значка.

Windows, macOS, Microsoft VS Code и Remote не проверены. Новая сверка конкретных
UUID с Конфигуратором и штатной выгрузки без поддержки остаётся открытым пунктом приёмки.

Большая бухгалтерия из playground проверена в нативном Extension Host:
81 464 файла, 557 групп точных путей, 76,6 секунды от активации до применения
защиты с отладочным backend; последующий запрос корня — 35 мс. Нативный ввод
в запрещённый BSL заблокирован. SHA-256 корневого XML и файла правил не изменились.
После изменения порядка загрузки тест с оптимизированным backend завершился за
22,2 секунды, первые подтверждённые ограничения появились через 0,75 секунды.
Это весь нативный сценарий с открытием модуля, а не чистое время парсинга.
Прелоадер скрывает дерево до полной готовности. Проверены одинаковая перезапись,
изменение, удаление/восстановление правил и сохранение BSL без нового обхода.
Отдельный тест групп проверил буквальные запятые/скобки в имени и редактирование
соседнего файла. Первоначальный вариант с 71 тысячей отдельных ключей вызывал
неотзывчивость окна и заменён компактными группами.

Публичные API: [FileDecoration](https://code.visualstudio.com/api/references/vscode-api#FileDecoration).
Приоритет сессионной настройки: [VS Code 1.109.0 FilesConfigurationService](https://github.com/microsoft/vscode/blob/1.109.0/src/vs/workbench/services/filesConfiguration/common/filesConfigurationService.ts).
