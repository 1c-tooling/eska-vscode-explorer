# Правила поддержки 1С

Настройка `eska.explorer.supportPolicy` (по умолчанию `true`) включает проверку
для всех папок текущего окна. Установите `false`, чтобы загружать дерево без
проверки поддержки, её значков и ограничений ESKA. Изменение применяется без
перезапуска: текущая проверка перестаёт публиковать результаты, собственные
ограничения снимаются, пользовательские сохраняются. Повторное включение
запускает проверку с использованием актуального кеша. Описанное ниже поведение
относится к включённой настройке.

ESKA читает правила в Rust-backend. С capability `supportFiles` дерево появляется
сразу: проверяются только открываемые файлы и дескрипторы видимых объектов.
Полный список файлов и десятки тысяч ограничений не загружаются при старте.
При первом открытии проверяются правила и XML владельца, при повторном — их
текущие байты с повторным использованием разобранных данных.

Запрещённый файл открывается в защищённой вкладке. Обычная неизменённая вкладка,
открытая через Explorer, Quick Open или поиск, после проверки также переводится
в защищённый источник. Сессионная команда «Настроить активный редактор доступным»
не снимает запрет этого источника. Файл с разрешением «редактируется с сохранением
поддержки» остаётся обычным редактируемым файлом. Неизвестное состояние допускает
только чтение до успешной проверки.

Подключение начинается без раскрытия панели ESKA. Папки VS Code workspace
используют независимые backend-сессии; UUID разных проектов не смешиваются.
Старый backend без `supportFiles` обслуживается прежним постраничным методом;
для быстрого старта нужен backend API 1.3.

| Оранжевый маркер слева | Значение |
|---|---|
| `lock` | Изменения запрещены правилами поддержки |
| `lock_open_right` | Редактирование с сохранением поддержки |
| `no_encryption` | Объект снят с поддержки |
| Без маркера | Собственный объект или состояние поддержки не определено |

Маркер объединён со значком типа метаданных в одном SVG: тип остаётся виден,
маркер расположен в нижнем правом углу значка. Цвет маркера — оранжевый во всех
четырёх темах. Справа остаётся Git-статус и его цвет. Если данные поддержки определить не удалось,
маркер поддержки не показывается; причина доступна в подсказке объекта. Группы не
наследуют замок дочернего объекта.

После адресной проверки готовая иконка входит в TreeItem синхронно; до получения
статуса узел доступен без маркера поддержки. Очередь Git не задерживает известный
статус. Варианты SVG готовятся при сборке расширения.
Использованы [Material Symbols Google](https://github.com/google/material-design-icons),
лицензия Apache 2.0 включена в пакет.

Для обычного Explorer используются реальные файловые URI и прежние текстовые
бейджи `🔒`, `S` для определённых состояний: его API не позволяет расширению
назначать эти SVG по статусу. Открытие исходника из дерева ESKA, включая
раздел файлов, выбирает защищённую вкладку по актуальным правилам. Если XML содержит
объекты с разными разрешениями, весь XML открывается read-only; tooltip сообщает
о совместном хранении. В дереве разрешённый объект сохраняет свой собственный
статус. Отдельный разрешённый модуль остаётся редактируемым.

## Механизм read-only

Для открытия заблокированных файлов зарегистрирован файловый источник
`eska-protected:` с неизменяемым свойством `isReadonly: true`. Он читает те же
байты с диска и следит за изменениями исходника, но отклоняет операции записи.
VSCodium проверяет запрет всего файлового источника раньше сессионной команды.
Для разрешённого файла ESKA открывает обычный `file:` URI; добровольная блокировка
пользователя работает как прежде. После изменения правил открытая защищённая
вкладка остаётся доступной только для чтения; повторное открытие исходника из
ESKA выбирает новый режим. То же относится к отключению проверки поддержки:
уже открытая защищённая вкладка остаётся только для чтения до повторного открытия.
Команда «Показать активный файл в дереве» сопоставляет
защищённую вкладку с исходным файлом.

Нативные видимые вкладки проверяются при открытии; неизменённые запрещённые
документы переводятся в `eska-protected:`. Грязный документ автоматически не
закрывается и не заменяется: его несохранённый текст остаётся в обычном редакторе
с read-only настройкой и предупреждением. Эту сессионную настройку пользователь
может снять вручную. Расширение не подменяет встроенный `file:` provider.
Некоторые языковые расширения, принимающие только `file:`, могут не обрабатывать
защищённые вкладки. Защита не распространяется на терминал и произвольный внешний ИИ.

Используется `files.readonlyInclude` в области Workspace с точными абсолютными
путями только проверенных файлов; при необходимости они объединяются в группы альтернатив
внутри одного верхнего каталога исходников, без wildcard-запрета на соседние
файлы. Общие начало и конец путей вынесены
за скобки альтернатив, чтобы уменьшить размер настроек; вложенные группы
альтернатив не используются. ESKA сохраняет в workspaceState журнал SHA-256
принадлежащих ей ключей вместо копии длинных путей; прежний журнал мигрирует
автоматически. Полные шаблоны остаются в настройках. Расширение учитывает
существующие правила и удаляет только собственные неизменённые ключи при
пересчёте, отключении подключения и деактивации. Другие пользовательские правила,
включая добровольную блокировку `.bsl` и `.os`, сохраняются. Изменения настроек,
пришедшие одновременно с записью ESKA, учитываются отдельно.

Права ОС не меняются. ESKA никогда не
вызывает `setActiveEditorWriteableInSession` и не сбрасывает сессионные блокировки.
Если документ уже изменён, его текст, вкладка и позиция сохраняются; при новом
запрете показывается предупреждение. Автоматического сохранения или отката нет.

**Ограничение обычных файлов снимается штатной командой read-only.** Команда
`workbench.action.files.setActiveEditorWriteableInSession` имеет приоритет над
настройками файла, но не над запретом источника `eska-protected:`. Её действие
сохраняется при последующих изменениях настроек read-only в этой сессии.
Пользовательские `files.readonlyExclude` тоже могут исключить обычный файл из
действия include. Значок показывает правило поддержки, а не тип уже открытой вкладки.

Сохранённые настройки могут остаться после аварийного завершения Extension Host;
журнал используется при следующем подключении/деактивации. Это отличается от
нормального отключения, для которого выполняется очистка. Удаление расширения
после аварии без повторного запуска не даёт ему выполнить очистку; принадлежащие
ему точные пути тогда нужно удалить из `files.readonlyInclude` вручную.

## Обновление и неизвестное состояние

Изменения XML и правил поддержки, ручное обновление и переподключение
инвалидируют статусы затронутой сессии. Дерево остаётся доступным. Ответы прежних
сессий или поколений отбрасываются. Перед открытием файл проверяется заново,
даже если файловый наблюдатель ещё не сообщил о переключении ветки.

Backend сверяет SHA-256 текущего файла правил и цепочки дескрипторов владельца.
Кеш зависит от содержимого, поэтому переход A → B → A не требует полного обхода
и не использует разрешение другой версии XML. При отсутствии, повреждении правил,
неизвестном владельце или неоднозначном XML файл остаётся доступным только для
чтения. Это неизвестное состояние, а не утверждение о фактической поддержке.

Подключение с `diskCache:true` сохраняет разобранные зависимости в
`.eska/cache/metadata`. Перед использованием читаются текущие исходные байты;
полный fingerprint проекта для адресного запроса не строится. Сохранение
содержимого известного BSL не требует повторного анализа поддержки.

При отключении удаляются только собственные правила редактора. Следующий запуск
применяет ограничения лишь для затребованных файлов. При обновлении со старого
клиента прежний большой список ограничений очищается однократно; миграция может
занять время редактора. Уже открытая защищённая вкладка остаётся read-only до
повторного открытия даже после разрешения редактирования или отключения настройки.

Backend без `supportPolicy` остаётся пригоден для навигации; защита не объявляется
работающей. Правила поддержки, UUID и исходники открытием проекта не изменяются.
Корректность произвольных правок BSL/XML эта функция не проверяет.

## Фактические проверки

Адресная проверка, Linux/VSCodium 1.109.5: дерево доступно при искусственно
задержанном запросе поддержки; обычное открытие переводится в read-only provider,
сессионное снятие запрета не позволяет печатать, `workspace.fs.writeFile`
защищённого URI отклоняется. Проверены правила A → B → A, неизвестное состояние,
разрешённый модуль, сохранение грязного буфера и отсутствие `metadata/support`.

На большой конфигурации `big_configuration_temp/src/buhmfo` с release-backend:
дерево готово за 435 мс; проверка модуля — 672 мс; защищённая вкладка открыта
за 954 мс после начала открытия. Получен один файл и применено одно правило.
SHA-256 корня, правил, дескриптора и BSL совпадают до и после проверки.

Исторические проверки постраничного режима, Linux/VSCodium 1.109.5: обычные файловые URI, открытие до раскрытия дерева,
смешанный XML, разрешённый отдельный модуль, пользовательские BSL/OS-блокировки,
грязный документ, переключение веток, повреждение правил, сессионная
разблокировка, очистка настроек и две папки workspace с одинаковыми UUID,
удаление выбранной папки и сохранение защиты при обрыве второй backend-сессии.
Дополнительный нативный тест подтвердил, что защищённые BSL и XML не принимают
ввод после сессионной команды, прямой `workspace.fs.writeFile` отклоняется,
открытый BSL обновляется после внешней правки, а снятие запрета возвращает
обычный файловый URI с независимой добровольной BSL-блокировкой.

Скриншоты настоящего дерева: [тёмная](measurements/support-policy/support-dark.png),
[светлая](measurements/support-policy/support-light.png),
[контрастная](measurements/support-policy/support-contrast.png),
[светлая контрастная](measurements/support-policy/support-contrast-light.png).
На них Locked имеет одновременно правило поддержки и Git M; tooltip проверен
тестом, Git-цвет сохранён. Own и Removed не получают ограничивающего значка.

Windows, macOS, Microsoft VS Code и Remote не проверены. Новая сверка конкретных
UUID с Конфигуратором и штатной выгрузки без поддержки остаётся открытым пунктом приёмки.

Большая бухгалтерия из playground проверена в нативном Extension Host:
81 464 файла, 557 групп точных путей, 76,6 секунды от активации до применения
защиты с отладочным backend; последующий запрос корня — 35 мс. Нативный ввод
в запрещённый BSL заблокирован. SHA-256 корневого XML и файла правил не изменились.
После изменения порядка загрузки тест с оптимизированным backend завершился за
22,2 секунды, первые подтверждённые ограничения появились через 0,75 секунды.
Это весь нативный сценарий с открытием модуля, а не чистое время парсинга.
В том режиме прелоадер скрывал дерево до полной готовности. Проверены одинаковая перезапись,
изменение, удаление/восстановление правил и сохранение BSL без нового обхода.
Отдельный тест групп проверил буквальные запятые/скобки в имени и редактирование
соседнего файла. Первоначальный вариант с 71 тысячей отдельных ключей вызывал
неотзывчивость окна и заменён компактными группами.
