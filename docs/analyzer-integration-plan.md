# Модульные backend ESKA и встроенный LSP-клиент

План от 2026-10-20. T90, T83, T91, T84, T92–T97 и T85–T89 завершены
для зафиксированной Linux-матрицы. T88 проверила защиту правок, обновление
XML/BSL, все sources приложения, protected bridge и два окна с config leases.
T89 завершена 2026-10-22 с решением пользователя отложить измеренные
превышения производительности в T106. База Explorer — `main`
на `a0a02a9` (0.0.12), база ESKA — `86ef141` (0.14.3).
Цель: одним расширением установить только `eska-project` и внешний bsl-analyzer
и получить дерево, подсветку и языковые функции для Designer XML.
Полная `eska`, check/build/VCS/debug для Explorer не требуются.

Основной план и статусы T83–T99 находятся в
[репозитории ESKA](https://github.com/1c-tooling/eska), файл
`docs/roadmap/15-designer-xml-analyzer.md`.
При соседнем расположении checkout доступен
[локальный план](../../eska/docs/roadmap/15-designer-xml-analyzer.md).
Этот документ фиксирует работу клиента; схема проекта определяется только ESKA.

T106 — `IN-PROGRESS`: исправлены повторное подключение одного проекта,
очистка diagnostics на каждую правку и повторная подготовка current-конфига.
Новая серия на `buhmfo` проходит 9 из 12 исходных gates T90. Остаются запуск
языка в обоих режимах и definition repeat; допуски не изменены
([локальный отчёт](../../eska/docs/roadmap/17-language-performance.md),
[измерения](measurements/t106-language.json)).

По запросу от 2026-10-21 отдельно запланирован редактор запросов T100–T105:
`eska/docs/roadmap/16-query-editing.md`
([локальный план](../../eska/docs/roadmap/16-query-editing.md)).
Все задачи — `PLANNED`, после T89, независимо от T98–T99; текущая очередь
и приёмка T88–T89 не расширяются.

## Запланированное редактирование запросов

Одна модель сессии обслуживает запросы СКД, динамических списков и строковые
литералы BSL. Explorer показывает чистый SDBL без служебных `|` и экранирования,
а project backend отвечает за источники, контекст, кодирование и планы правок.
Designer XML/BSL остаются исходниками; отдельный `.sdbl` в проекте и шаг
материализации при сборке не требуются. `eska.toml` остаётся первичным конфигом,
языковые функции предоставляет внешний опубликованный bsl-analyzer без форка.

| Этап | Работа клиента |
|---|---|
| T100 | Согласовать с backend контракт владельца, снимка, карты позиций и обратной записи XML/BSL |
| T101 | Узлы запросов СКД/списков, редактируемые вкладки, точечное сохранение XML, конфликты и восстановление черновика |
| T102 | ПКМ в BSL, чистый черновик, блокировка исходного документа и его представлений, явные «Применить»/«Отмена», единый Undo |
| T103 | Проверить мост актуального черновика к своему LSP, перевод позиций ответов и правок, контекст XML-владельцев и границы upstream |
| T104 | Конструктор того же черновика, минимальные правки с сохранением комментариев и неподдерживаемых фрагментов |
| T105 | Установленный VSIX, реальные backend, сохранённые и изменённые буферы, два окна и измерения на копии buhmfo |

Для BSL черновик начинается с несохранённого буфера владельца. Autosave
черновика не применяет его к модулю; применение оставляет модуль изменённым
без автоматического сохранения. Исходная блокировка и пользовательские
read-only правила восстанавливаются при завершении сессии. Чтение с диска через
`eska-protected:` не подменяет проверку временной блокировки изменённого буфера.
Внешние изменения проверяются по версии/fingerprint до записи. Динамическая
сборка запроса из выражений не преобразуется в цельный литерал.

T103 сначала подтверждает работу подсказок/диагностики по изменённому черновику,
а не по старому тексту владельца. Мост BSL не считается подтверждением поддержки
СКД и списков; отсутствующая upstream-возможность явно остаётся непроверенной.
Новый процесс/индекс на каждый запрос и скрытая зависимость от собственной
сборки анализатора не добавляются. Подробные критерии и зависимости находятся
в основном плане T100–T105; ниже сохраняется план поставки T83–T99.

## Принятые границы

- `eska.toml` и member manifests — первичный конфиг. ESKA разрешает контекст
  приложения и генерирует обычный `bsl-analyzer.toml`, включая политику из
  `[tools.bsl-analyzer]`. Генерация и миграция не реализуются повторно в TypeScript.
- Метаданные обслуживает `eska-project serve`, выделяемый из существующего
  `eska ide`. Explorer подключается к нему напрямую по Metadata API; языковые
  запросы идут отдельным соединением по LSP, не через проектный сервер.
- Explorer содержит собственный `vscode-languageclient` и базовую грамматику.
  bsl-analyzer остаётся опубликованным upstream-бинарником без форка,
  vendoring или встраивания Rust-ядра. Принятия наших PR не требуется.
- `eska-project` устанавливается отдельно в общий каталог инструментов ESKA;
  установленный совместимый компонент переиспользуется. Для анализатора
  добавляется управляемая установка проверенной версии и явный путь
  к пользовательскому бинарнику. Установка выполняется на workspace host.
- Конфликт с `elishevkirill.bsl-analyzer-lsp` приостанавливает собственный
  клиент, включая незавершённый запуск/перезапуск, и показывает предупреждение.
  Дерево, свойства и базовая подсветка продолжают работать.
- Наличие бинарника не считается конфликтом. `isActive === false` не означает,
  что стороннее расширение отключено. Проверки выполняются до запуска,
  после асинхронных операций и при `extensions.onDidChange`.
- Собственный клиент возобновляется после устранения конфликта и повторной
  проверки контекста, если пользователь разрешил языковую часть. Принудительное
  отключение чужого расширения и завершение чужих процессов не применяются.
- LSP использует настоящие URI и несохранённый текст. Protected documents
  и проверки всех целей WorkspaceEdit сохраняют policy ESKA.
- Перенос отладчика, новый дизайнер форм, multi-root и изменения release
  automation не входят в работу Explorer. Отдельные `eska-check`, build/VCS,
  общая команда и выборочная поставка описаны в основном плане; отладка —
  опциональные T98–T99 после основной приёмки.
  Новые команды Git/build в Explorer этим планом не добавляются.
  Работающий сервер обновляется только по проверенному контракту совместимости.

## Порядок работ

Сначала в ESKA выделяется ядро и контекст приложения (T90 → T83), затем
проектный CLI и общий генератор (T91 → T84). После T92 сервер доступен
для разработки по явному пути. CI-проверка, build/VCS и делегирующая команда
выделяются в T93–T96; выборочные пакеты T97 нужны до установки из Explorer.
Номера T83–T89 сохранены; текущие статусы находятся в основном плане.

| Этап | Работа в Explorer | Зависимость |
|---|---|---|
| T83–T84 | Согласовать JSON-контракт подготовки и ошибки, не читать ESKA TOML самостоятельно | Ядро T90, модель T83, project T91 и генератор T84 |
| T92 | Подключить `eska-project serve`, проверить identity/capabilities и переход настройки пути со старого backend | T84; локальный бинарник до готовности пакетов |
| T85 | Установка только project/analyzer, отдельные индикаторы и независимые обновления, локальные бинарники и отмена | T92 и выборочные пакеты T97; переиспользовать `BackendSetup` / `installation` |
| T86 | Подключить грамматику, LSP lifecycle и языковые providers, включить runtime-зависимости в VSIX | T84–T85 |
| T87 | Реализовать состояние `suspended-conflict`, предупреждение и возобновление | T86 |
| T88 | Согласовать XML/BSL refresh, protected URI, отмену старых ответов и все пути WorkspaceEdit | T84, T86–T87 |
| T89 | Минимальная установка, чистые профили, настоящие бинарники, VSIX и измерения `buhmfo` | T83–T88 и T90–T97 |

В T92 задаётся миграция `eska.explorer.executable` и аргументов запуска.
Путь к старому `eska` или собственной сборке не переписывается молча:
проверяется выбранный компонент, показывается понятное действие для перехода.
Новый клиент не запускает полную ESKA как скрытую зависимость. Совместимость
документированной команды `eska ide` сохраняется общей оболочкой в T96.

UI установки показывает компоненты и версии одним сценарием. Установка
анализатора не должна требоваться для исправной работы дерева. В состоянии
конфликта автоматический запуск собственного клиента отменяется, а не
возобновляется очередным retry. Предупреждение появляется один раз на
событие конфликта; состояние остаётся видимым после закрытия уведомления.
Действия открывают управление расширениями или оставляют внешний анализатор.
Новые сообщения и команды локализуются на русский и английский.

## Строка состояния и обновления

Сохраняются два отдельных элемента внизу: `BSL Analyzer v…` и `ESKA v…`.
У анализатора тот же сценарий, что у ESKA: версия выбранного бинарника,
путь и состояние в подсказке, проверка обновлений по нажатию и через палитру.
Индикатор ESKA показывает версию фактически подключённого `eska-project`,
а не оболочки; имя компонента указано в подсказке.
Предлагаемая версия не подменяет установленную.

Проверки независимы: у каждого компонента свои настройка, время последней
проверки, доступный релиз и состояние операции. Фоновая проверка выполняется
не чаще раза в сутки для каждого компонента на своём host; ручная доступна
без ожидания этого интервала. `eska.explorer.checkForUpdates` остаётся настройкой
только ESKA. Ошибка, отмена, занятость или отключение проверок одного бэкенда
не блокируют другой. Уведомления называют конкретный компонент и обе версии;
обновление устанавливается по явному действию и не обновляет второй бэкенд.
Совместимость проверяется с текущей парой; несовместимость объясняется до записи.

В общей установке ESKA обновляется только project-компонент, без обязательного
обновления всего комплекта; анализатор обновляется в управляемом хранилище.
Это изменение прежнего контракта обновления монолитной ESKA документируется
при реализации T85/T97. Явно выбранный пользовательский бинарник не перезаписывается.
Подсказка и предложение обновления различают используемый бинарник и
управляемую установку. После обновления отображается проверенная фактическая
версия, другой сервис без необходимости не перезапускается.

При конфликте индикатор собственного анализатора остаётся с причиной
приостановки и указанием принадлежности Explorer. Проверка обновлений доступна,
но её завершение или установка не запускают приостановленный клиент.
Индикатор стороннего расширения не изменяется.

## Проверки

Используются существующие [проверки разработки](development.md) и
[Extension Host acceptance](acceptance.md), с новой матрицей:

1. Только Explorer: грамматика работает до индексации; диагностики, completion,
   hover и переходы приходят от собственного клиента с реальным сервером.
2. Оба расширения включены: своего клиента нет, дерево работает, предупреждение
   не повторяется при открытии файлов. Проверяется также ещё не активированный
   сторонний клиент.
3. Установка/включение стороннего расширения во время подготовки или работы:
   собственный запуск отменяется либо клиент останавливается.
4. Отключение/удаление стороннего расширения: корректное возобновление,
   в том числе после требуемого редактором перезапуска.
5. Ошибки сети/установки/версии, закрытие окна, падение сервера и два окна:
   нет потерянных настроек, бесконечных retry и оставшихся собственных процессов.
6. Защищённые исходники: все targets редактирования, включая resource operations,
   проверяются до применения; запрещённый edit отклоняется целиком.
7. Собранный VSIX работает без runtime-зависимостей из checkout и без расширений
   основного пользовательского профиля.
8. Отдельные индикаторы, команды и фоновые проверки: обновление доступно только
   для ESKA, только для анализатора или для обоих; настройки и суточные интервалы
   независимы. Ошибка/отмена одного компонента не мешает другому. Проверяются
   пользовательский бинарник, несовместимый релиз, обновление фактической версии
   и сохранение приостановки клиента при обновлении во время конфликта.
9. В окружении только project/analyzer: нет скрытого запуска полной `eska`,
   check/build/VCS/debug или поиска их в пользовательском PATH; дерево работает
   и без анализатора. Проверяются переход со старого backend, явный путь,
   несовместимый Metadata API и сохранность соседних установленных инструментов.

Для сценариев создаются отдельные `--user-data-dir` и `--extensions-dir`
в собственном подкаталоге соседнего `eska-playground`. `ESKA_TEST_ROOT`
вычисляется относительно репозитория. Глобальные установки и профиль
пользователя не используются для проверки установки.

На изолированной копии Designer XML `buhmfo` сравниваются внешний и встроенный
клиенты при одинаковой версии сервера и настройках: готовность дерева/анализа,
RSS/PSS, CPU, дисковая активность, кэши, задержка правки и навигации.
Формат отчёта и критерии — в T89 основного плана. Результаты Linux,
Windows, macOS, VS Code/VSCodium и Remote учитываются отдельно.

README, component-setup, development и packaging описывают собственный клиент
T86–T87 в этой ветке. Защита языковых правок и полная приёмка остаются
работами T88–T89; их сценарии ниже не объявляются пройденными.

## Проверка T92

На Linux x86_64 прошли typecheck и 143 Node-теста с настоящими `eska-project`
(API 1.12) и прежним `eska` (API 1.11, явный legacy). Нативные профили
VSCodium 1.109.5: общее дерево, свойства, legacy и пользовательский путь
с отклонением старого CLI — passed. Переподключение завершает принадлежащие
клиенту процессы; fallback на монолит отсутствует. Исправлено ожидание теста
для существующей свёрнутой группы Modules, без смены продуктового значения.

До T97/T85 project mode использует локальный или уже установленный компонент.
Установщик и проверка обновлений монолита доступны только в явном legacy mode.
Windows/macOS и Remote ожидают матрицы приёмки T89.


## Проверка T85

Установка project и upstream Analyzer, отдельные индикаторы, команды и суточные
проверки реализованы. Формат project ZIP/receipt и общий lock совместимы с
обновлённым Python CLI T97. [Руководство](component-setup.md),
[результаты и ограничения](measurements/t85-setup.json). Публичный project ZIP
ещё не опубликован; реальная минимальная установка использует локальный архив.
LSP-клиент и конфликт расширений не включаются в результат T85.

## Проверка T86

Собственные грамматики BSL/SDBL и BSL LSP-клиент работают с опубликованным
Analyzer 0.3.2, без внешнего расширения. Проверены чтение и несохранённые
диагностики, отмена подготовки, передача/release lease и ограниченный shutdown.
Runtime клиента и лицензии входят в VSIX. [Описание](language-service.md),
[результаты](measurements/t86-language.json). Format, rename, code actions
и серверные WorkspaceEdit закрыты до T88. На момент проверки T86 последующие
T87–T89 ещё не были завершены; результат T87 приведён ниже.
По решению пользователя приёмка выполняется в текущем Linux/VSCodium;
Windows, macOS, VS Code и Remote остаются непроверенными.

## Проверка T87

Конфликт известного расширения обрабатывается до запуска и после асинхронных
границ. Пройдены гонки подготовки, acquire/initialization, независимого обновления
и запоздалого выбора уведомления. Настоящий реестр VSCodium подтвердил установку,
удаление и три запуска одного профиля с enabled/disabled/re-enabled fixture.
Этот fixture не содержит языка: работа настоящего стороннего клиента 0.1.12
с опубликованным Analyzer 0.3.2 проверена отдельным профилем. Hover отвечает,
его процесс остаётся живым после остановки клиента Explorer, конфиг не меняется.
Тест не утверждает исправность произвольной версии стороннего расширения.
[Поведение](language-service.md#конфликт-расширений), [результаты](measurements/t87-conflict.json).

## Частичная T88: защита текстовых правок

Format, rename, code actions и server apply проверяют полный набор целей через
backend policy, версии буферов, состояние сессии и файлов. Пользовательские
read-only правила сохраняются. Одна запрещённая цель отменяет весь текстовый
edit; resource operations и неизвестные команды не исполняются. Устаревший
quick fix повторно не применяется. [Поведение и команды](language-service.md#защита-языковых-правок),
[отчёт](measurements/t88-language-edits.json).

XML/BSL refresh, смена ветки, корневой descriptor и манифест проверены нативно
в следующей части T88: [поведение](language-service.md#изменения-исходников-и-контекста),
[отчёт](measurements/t88-language-refresh.json). Итоговая часть T88 проверила
смену приложения, protected bridge своего LSP, два окна и наблюдение/права
sources вне выбранного member: [отчёт](measurements/t88-integration.json).
T89 затем подтвердила окончательную матрицу и измерения `buhmfo`
относительно замороженного baseline: [результаты](language-service.md#t89-сверка-результатов-и-большой-контекст).
