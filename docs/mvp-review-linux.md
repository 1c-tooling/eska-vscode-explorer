# Ревью перед MVP: eska и Explorer

Дата: 2026-09-19. Проверены `eska` (`feat/ide`, исходный `f97effe`) и
Explorer (`feat/explorer`, исходный `544fa3c`). Исходные рабочие копии были чистыми.
Область: процессы, отмена, обновления, кеш, смена веток, несколько проектов,
поиск, большие группы и память. Приёмка T81 остаётся открытой.

## Замечания по приоритету

Все перечисленные исправления покрыты повторными проверками ниже. P1 означает
нарушение жизненного цикла или обычной работы дерева; P2 — задержки и удержание
ресурсов; P3 — частный случай обнаружения CLI.

| Приоритет | Причина и проявление | Исправление |
| --- | --- | --- |
| P1 | Отключение во время проверки CLI не отменяло `ensure`: поздний результат мог снова подключить backend. | Контроллер отмены охватывает выбор проекта и preflight; после ожиданий проверяются отмена и наличие папки. `extension.ts`. |
| P1 | Проверки версии/обновлений жили отдельно от владельца. SIGTERM-устойчивый процесс переживал таймаут, а закрытие IDE не дожидалось проверки или очистки установки. | Общий отменяемый `runProbe` ждёт закрытия child и использует SIGKILL для read-only probes. `BackendSetup.shutdown` отменяет IO, завершает собственную задачу и ждёт очистки. `installation.ts`, `backend-setup.ts`, `process.ts`. |
| P1 | Запрос, уже стоявший за обновлением, получал `stale_generation` и запускал ещё одно полное обновление, хотя событие уже обработано. На большом стенде это воспроизвелось как каскад refresh и `sourceChanged`. | При уже известном новом поколении повторяется только запрос. Потеря события по-прежнему требует синхронизации. `tree.ts`. |
| P2 | Отмена поиска откладывала отклонение Promise до ответа backend; новая выдача ждала старую работу. | Promise отклоняется сразу, ID сохраняется до ответа: поздний ответ допустим, очередь остаётся ограниченной. `process.ts`. |
| P2 | После удаления последнего ребёнка пустая группа больше не раскрывалась и не удаляла старых потомков; Git-декорации удерживали удалённые узлы сильными ссылками. | Пустая ветка сразу очищает потомков; устаревшие записи не могут повторно загрузиться; декорации используют слабые ссылки и очищают недействительные ключи. `tree.ts`, `decorations.ts`. |
| P2 | Полный refresh многократно обходил индекс путей при сворачивании каждого владельца и сохранял заведомо устаревшие записи поиска. | Индекс путей очищается один раз на пакет; полный поиск начинает перестроение с корня без старых записей, локальный refresh сохраняет незатронутые записи. `eska/src/project/metadata_workspace/refresh.rs`. |
| P2 | Простаивающий backend опрашивал очередь каждые 2 мс. | Ожидание через `thread::park/unpark`; запрос, остановка и writer будят worker. `eska/src/cli/ide/runtime.rs`. |
| P2 | При ошибочном HTTP-статусе тело ответа не закрывалось; загрузка не была связана с закрытием расширения. | Тело отменяется, загрузка получает сигнал владельца и ограничение времени. `installation.ts`. |
| P3 | Каталог с именем `eska` и правом X в начале PATH принимался за CLI. | После проверки доступа проверяется тип файла; порядок настоящих исполняемых файлов сохранён. `installation.ts`. |

Архитектурные изменения ограничены владельцами уже существующих ресурсов.
Убраны повторные проверки CLI после установки: `perform` возвращает единственный
проверенный результат. Не добавлены runtime-зависимости, альтернативный XML parser
или новый async runtime. Wire API, JSON-схемы и требования совместимости сохранены.

Коммиты исправлений:

- eska: `92c2ef3 perf(ide): Устранены периодические пробуждения простаивающего процесса`;
- eska: `4fb030e perf(metadata): Ускорены полное обновление дерева и перестроение поиска`;
- Explorer: `12bc1c9 fix(lifecycle): Отменены незавершённые подключения и проверки CLI при закрытии`;
- Explorer: `787428b fix(tree): Устранены повторные обновления и удержание удалённых узлов`.

Node 22.23.1; VSCodium 1.109.5, Extension Host Node 22.21.1.
Backend 0.11.2 собран с `cargo build --profile dist`; установленный VSIX — 0.0.2.
Собиралась только Rust CLI. Сборка/выгрузка большой конфигурации не запускалась.

в sandbox эта среда не давала дочерним процессам нормальный stdout и запрещала
локальные sockets. Это не заменялось mock-прохождением.
Установка/обновление проверяется на собственных fake CLI и фасаде VS Code Tasks:
ошибка, отказ, быстрое завершение, отмена, lock, несколько копий PATH, несовместимый
API/capabilities, HTTP-ошибки, ограничения загрузок. Пользовательская CLI не обновлялась.

## Большой стенд

Реальный workspace из двух проектов; раскрываются 3 808 общих модулей и 636 макетов.
Все 101 999 исходных XML/BSL сверены по SHA-256 до/после: изменений нет.
Дисковый кеш сохранён, кеш ОС не сбрасывается; каждый цикл создаёт новый backend.
Это измерение native API/provider/модели Quick Pick, а не последнего нарисованного
пикселя. Во время серии не запускались сборки и хеширование.

## Оставшиеся ограничения

**P2: бюджет памяти Extension Host пока не выполнен.** В большой серии максимум
VmHWM backend — 215.6 MiB, всего Extension Host — 379.6 MiB при бюджете 256 MiB.
После отключений RSS Extension Host: 316.6, 295.3, 317.9, 302.5, 372.3 MiB.
В этот процесс входят редакторы, встроенные службы IDE и тестовый runner.
Эти числа не доказывают утечку именно дерева и не позволяют закрыть бюджет.

В отдельной серии из 20 переподключений после принудительного GC heap всего
Extension Host вырос с 25.2 до 32.5 MiB; конечный RSS — 204.4 MiB. Проверяемые
объекты подключений освобождены на каждом цикле, набор сохранённых ключей
раскрытия постоянен (3). Источник оставшегося роста heap не установлен;
отсутствие любых утечек не утверждается. Эта серия не открывает BSL-редакторы
и не сопоставима напрямую с пиком полной UI-серии.
[Неокруглённые измерения памяти](measurements/mvp-memory-linux.json).

Windows/macOS/Remote и Microsoft VS Code отдельно от VSCodium в этой проверке
не запускались. Реальная загрузка и замена пользовательской CLI из Интернета
не выполнялась. Принудительное убийство IDE ОС не гарантирует очистку install-lock;
порядок ручного восстановления описан в [управлении CLI](cli-management.md).
Полная выдача Quick Pick включает 250 мс debounce; открытие больших BSL и первое
раскрытие тысяч строк имеют расходы самого редактора и не равны backend-бюджетам.

## Воспроизведение

Команды запускаются из корня Explorer после компиляции и упаковки VSIX:

```sh
ESKA_TEST_BINARY="$(realpath ../eska/target/dist/eska)" \
ESKA_TEST_ROOT="$(realpath ../eska-playground)" \
ESKA_TEST_VSIX=/tmp/eska-explorer-review-0.0.2.vsix \
ESKA_PERF_PROJECT="$(realpath ../eska-playground/big_configuration_temp)" \
ESKA_PERF_RESULT=/tmp/eska-review-performance.json \
VSCODE_EXECUTABLE=codium node test/run-host.mjs test/performance-host.cjs
```

Для 20 циклов проверки освобождения объектов замените тест на
`test/memory-host.cjs`, а выходной параметр на
`ESKA_MEMORY_RESULT=/tmp/eska-review-memory.json`. Принудительный GC включается
только в этом тестовом host. `test/shutdown-host.cjs` использует маленький fixture
без `ESKA_PERF_PROJECT` и оставляет процесс работающим для проверки закрытия IDE.
