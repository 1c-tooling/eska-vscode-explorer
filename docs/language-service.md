# Собственный языковой клиент

T86 подключает `vscode-languageclient` 10.1.2 к опубликованному
`bsl-analyzer-app` 0.3.2 по stdio. Backend project использует Metadata API 1.12;
TypeScript читает его DTO, без собственного разбора `eska.toml` и Designer XML.
Проверенная среда — Linux x64 GNU, VSCodium 1.109.5, Extension Host Node 22.21.1.

## Запуск и контекст

Подсветка BSL/SDBL, комментарии, скобки и отступы принадлежат Explorer и доступны
без анализатора. LSP запускается при первом открытии BSL либо командой
`eska.explorer.restartLanguage`, независимо от видимости дерева. Открытие только
дерева не создаёт конфиг и не запускает индексатор.

До запуска клиент получает контекст, проверяет бинарник, вызывает
`analyzer/configStatus`, `analyzer/configPrepare`, затем `analyzer/acquire`.
Сервер читает обычный `bsl-analyzer.toml` в корне контекста: флаг `--config`
команде `lsp` не передаётся. Конфликт пользовательского или изменённого
управляемого конфига останавливает запуск с объяснением. Для чужого конфига
используется явная миграция ESKA с preview и сохранением оригинала.

`eska.explorer.selectAnalysisContext` запрашивает имя приложения из `eska.toml`;
проверку выполняет backend. При неоднозначности backend предоставляет список
для Quick Pick. Пустая строка использует его выбор по умолчанию. Успешный выбор
хранится в состоянии окна, без изменения манифеста. Параллельный multi-root
анализ не добавляется.

`eska.explorer.languageFeatures = false` останавливает собственный клиент,
сохраняя дерево и грамматики. Legacy backend без контракта конфигурации
объясняет недоступность LSP; ошибки языка не отключают сервер метаданных.
Индикатор Analyzer различает проверенный бинарник, подготовку, соединение,
ошибку и приостановку. Соединение не означает завершённую индексацию или
отсутствие диагностик.

## Возможности и границы

Проверены настоящие BSL hover, definition, document symbols, completion,
semantic tokens и диагностики несохранённого буфера. LSP получает настоящие
`file:` URI; содержимое на диске не заменяется тестовой правкой. Providers
чтения отбрасывают ответы после смены поколения клиента или версии документа.
Для отдельного `.sdbl` заявлена только TextMate-подсветка; семантическая
поддержка отдельного запроса этим этапом не подтверждена.

В текущей части T88 включены format/range/on-type format, rename, code actions
и серверный WorkspaceEdit с проверкой всех целей. Реальные rename, форматирование
и quick fix проверены в Linux/VSCodium с включённой policy. XML/BSL refresh,
смена ветки и переподготовка корневых входов проверены отдельным нативным
профилем. Проверены смена выбранного приложения, два одновременных окна и
собственный клиент с protected URI. T88 завершена для Linux/VSCodium;
окончательная приёмка и сравнение производительности на `buhmfo` относятся к T89.

## Изменения исходников и контекста

Существующий `ProjectWatcher` сообщает языковой сессии об изменениях сразу,
до отправки coalesced batch в Metadata API. Несохранённые BSL-правки и события
`metadata/changed` также меняют поколение модели. Общий request middleware
отбрасывает ответы прежней модели, клиента или версии документа; отложенные
quick fix сохраняют это поколение до применения.

Обычные XML и BSL обрабатывает инкрементальный watcher опубликованного сервера:
Explorer не посылает неподдержанные notifications и не перезапускает индекс
на каждое сохранение. После серии XML-изменений он проверяет
`analyzer/configStatus`. Пути корневых descriptors берутся из DTO backend.
Изменение корня или управляемого `bsl-analyzer.toml` приостанавливает выдачу
языковых результатов до проверки fingerprint. Новый конфиг готовится после
остановки собственного LSP и release lease. Ручной конфликт управляемого
конфига останавливает свой клиент и сохраняет файл. Смена `eska.toml`
сразу отзывает старые результаты, затем заменяет Metadata-сессию.

При одинаковом конфиге проверка сохраняет PID и уже показанные diagnostics,
даже если сервер не прислал новый push. Они возвращаются только актуальному
экземпляру и версии буфера. При замене
контекста они удаляются вместе с прежней сессией.

Нативный профиль подтвердил изменение разрешения BSL-вызова через XML-флаг
`Global`, Git round-trip, 30 быстрых правок с восстановлением diagnostics,
новый fingerprint после корневого XML, reconnect после манифеста и сохранение
ручной правки конфига. Эти результаты относятся к конкретным сценариям:
опубликованный сервер по-прежнему не сообщает версию push diagnostics.
[Отчёт](measurements/t88-language-refresh.json).

Если выбранное приложение включает sources вне открытого member, языковая
сессия наблюдает их файлы и манифесты тем же фильтром, что `ProjectWatcher`.
Наблюдатели удаляются вместе с сессией. Для проверки прав такие корни
подключаются через существующие `SupportContexts`, без второго разбора policy
в клиенте. Уже открытые backend scopes переиспользуются; при отключённой
support policy дополнительный индекс метаданных не запускается. Пока scope
не готов, языковая правка запрещена; запуск LSP его не ожидает.

Два окна могут читать один подготовленный конфиг. Переключение одного окна
на другое приложение запрещается, пока конфиг удерживает второе окно; файл
сохраняется, дерево и второй LSP продолжают работать. После release переключение
проходит. Выбранное приложение сохраняется при ручном рестарте, старые diagnostics
удаляются. Тест передаёт выбор контроллеру; работу с клавиатурой в Quick Pick
он не проверяет.

Нативная проверка protected bridge своего клиента подтвердила semantic tokens,
hover, definition, references, outline, folding и diagnostics; поздний настоящий
hover отброшен после изменения источника. Перезапуск восстанавливает providers,
а rename через `file:` alias запрещён backend policy. Реальное изменение
XML-свойства через Metadata API обновляет разрешение BSL-вызова без рестарта
LSP. [Результаты, границы и установленный пакет](measurements/t88-integration.json).

## Защита языковых правок

Разрешения определяет существующий backend `supportFiles`. Перед выдачей или
применением правки проверяются весь набор целей, поколение policy, версии
открытых буферов, состояние сессии, файлов и пользовательские
`files.readonlyInclude`/`files.readonlyExclude`. Цели должны быть обычными
каноническими `file:` внутри выбранного контекста; protected URI, URI с fragment
или query и symlink-псевдонимы отклоняются. При отказе одной цели весь edit
отклоняется с объяснением; пользовательские read-only правила сохраняются.

Rename требует версий от сервера. Если первый ответ содержит ещё не открытые
цели без версии, клиент открывает их в памяти и один раз запрашивает результат
повторно. Quick fix без версии допускается только для буфера, открытого на
момент запроса. Само действие хранит снимок до выбора в интерфейсе и повторно
проверяет права и актуальность перед применением. Серверный `workspace/applyEdit`
требует явных версий уже открытых целей. Запоздавшие действия не применяются
после изменения буфера или остановки сессии.

Клиент объявляет `resourceOperations = []`: create/delete/rename файлов
отклоняются целиком, неизвестные серверные команды не исполняются.
Для текстового edit используется одна транзакция публичного
[workspace.applyEdit](https://code.visualstudio.com/api/references/vscode-api#workspace.applyEdit).
Проверка server apply использует публичный
[middleware.workspace.handleApplyEdit](https://github.com/microsoft/vscode-languageserver-node/blob/release/client/10.1.2/client/src/common/client.ts).
Это не новые операции управления объектами метаданных.

[Машинный отчёт частичной T88](measurements/t88-language-edits.json)
отделяет реальные providers от инъекции server apply payloads и тестов гонок
с заменёнными границами. Совместные проверки приведены в
[итоговом отчёте T88](measurements/t88-integration.json).

Опубликованный сервер не передаёт версию в push diagnostics. Проверка правки
и восстановления подтверждает конкретный сценарий, но не доказывает отсутствие
устаревших diagnostic при любых быстрых правках.

## Конфликт расширений

T87 проверяет `elishevkirill.bsl-analyzer-lsp` через публичные
`extensions.getExtension` и `extensions.onDidChange`. Проверка относится к
текущему extension host; доступное, но не активированное расширение тоже блокирует
запуск. Наличие одного бинарника анализатора конфликтом не является.

Состояние `suspended-conflict` отменяет подготовку и перезапуск и завершает только
свой LSP перед освобождением lease. Дерево, свойства и грамматики остаются
доступны. Индикатор Analyzer сохраняется с версией выбранного бинарника, причиной
приостановки и указанием владельца ESKA Explorer. Проверка и установка обновления
не возобновляют LSP, пока конфликт сохраняется.

Предупреждение показывается один раз за период конфликта. Действие управления
открывает Extensions с фильтром по ID через публичную `workbench.extensions.search`.
Второе действие оставляет внешний клиент. Проверка конфликта не активирует,
не отключает и не удаляет стороннее расширение и не завершает его процессы.
Существующий мост protected documents может активировать языкового провайдера
для чтения. После подтверждённого
исчезновения расширения из реестра запускается новая проверка контекста;
пользовательское отключение языка сохраняется. Если редактор требует reload,
состояние остаётся приостановленным до изменения фактической доступности.

Проверки после асинхронных границ отбрасывают старые поколения, включая передачу
ответа acquire и LSP initialization. Закрытое или запоздавшее уведомление не
удерживает shutdown и не применяет действие к новому периоду конфликта.
Контракты: [extensions API](https://code.visualstudio.com/api/references/vscode-api#extensions),
[публичная команда поиска](https://code.visualstudio.com/api/references/commands).
Результаты: [T87](measurements/t87-conflict.json).

## Остановка

Каждая сессия владеет клиентом, процессом и config lease. При остановке сначала
отзываются ожидающие действия и до четырёх секунд ожидаются текстовые транзакции,
уже переданные редактору. По timeout пишется запись в журнал; отозвать уже
переданную транзакцию публичный API не позволяет. Затем завершается LSP и
подтверждается выход его процесса, освобождается lease,
после чего можно закрывать Metadata API. Отмена подготовки обрабатывает и передачу
уже выданного lease: полученный идентификатор освобождается до нового старта.
Диалоги не удерживают очередь shutdown. Ожидания ограничены; при необходимости
сигналы направляются только созданному процессу. Автоматического цикла
перезапуска после ошибки нет. Бинарник и процессы стороннего клиента не трогаются.

## Проверка

Из checkout Explorer, с собранным соседним project и явным бинарником upstream:

```sh
export ESKA_TEST_ROOT="$(realpath ../eska-playground)"
export ESKA_TEST_BINARY="$(realpath ../eska/target/debug/eska-project)"
export ESKA_TEST_ANALYZER_BINARY=/absolute/path/bsl-analyzer-app
export ESKA_TEST_LANGUAGE=1
export ESKA_HOST_SUPPORT_DISABLED=1
export VSCODE_EXECUTABLE=codium
node test/native-language-probe.mjs
node test/run-host.mjs test/grammar-host.cjs
node test/run-host.mjs test/language-host.cjs
ESKA_TEST_PYTHON="$(python3 -c 'import sys; print(sys.executable)')" \
  node test/run-host.mjs test/language-cancellation-host.cjs
```

Support policy в этих языковых профилях отключена явно: защита T88 здесь
не принимается. Runner использует собственные проект, профиль и extensions-dir
в `eska-playground`, после проверки удаляет их. Пользовательские расширения
не подключаются. `ESKA_TEST_VSIX=/absolute/path/package.vsix` включает установку
пакета и запуск именно его runtime. Нативная проверка грамматик использует
TextMate/Oniguruma текущего редактора. Raw LSP probe оставляет свой уникальный
стенд с отчётом для повторной проверки.

Unit/process tests входят в `node --test test/*.test.mjs` и `bun test`.
Результаты T86 и ограничения перечислены в
[отчёте проверки](measurements/t86-language.json).

Для проверки правок с включённой policy используйте те же binary variables
и отдельный запуск:

```sh
unset ESKA_HOST_SUPPORT_DISABLED
ESKA_HOST_LANGUAGE_EDITS=1 node test/run-host.mjs test/language-edits-host.cjs
```

Fixture поддержки синтетический; разрешения вычисляет настоящий project.
Rename, formatter и quick fix получают ответы настоящего опубликованного
анализатора. Server apply payloads подаются тестом в публичный middleware;
применение выполняет настоящий редактор. Проверяются смешанный XML, поздний
quick fix, версии, protected URI, операции с ресурсами, read-only правило
пользователя, побайтовая сохранность файлов и выход собственных процессов.

Для обновления модели используется свой Git-fixture и обычные native providers:

```sh
ESKA_HOST_SUPPORT_DISABLED=1 ESKA_HOST_LANGUAGE_REFRESH=1 \
  node test/run-host.mjs test/language-refresh-host.cjs
```

Этот профиль явно отключает policy, чтобы отдельно проверить свежесть модели.
Он создаёт и переключает только свои две ветки в удаляемом проекте runner.

Совместные сценарии T88 запускаются с теми же binary variables и
`ESKA_TEST_VSIX`, если проверяется установленный пакет:

```sh
unset ESKA_HOST_SUPPORT_DISABLED
ESKA_HOST_OWN_PROTECTED=1 node test/run-host.mjs test/protected-language-host.cjs
ESKA_HOST_LANGUAGE_MUTATION=1 node test/run-host.mjs test/language-metadata-mutation-host.cjs
node test/two-language-windows.mjs
ESKA_HOST_MEMBER_CONTEXT=1 node test/two-language-windows.mjs
```

Первые два профиля используют включённую policy. Runner двух окон отключает
её для проверки leases; профиль member затем включает её и проверяет
разрешённый rename. Два окна сохраняют координацию и отчёт в собственном
каталоге playground; временные профили редактора runner удаляет.
