# Компоненты Explorer

T85 добавляет установку и независимые обновления `eska-project` и опубликованного
`bsl-analyzer-app`. Дерево использует Metadata API 1.12; проверенная версия
анализатора — 0.4.0, CLI contract 3.5. T86 добавляет
[собственный языковой клиент](language-service.md). Состояние «бинарник проверен»
ещё не означает работающий LSP: клиент запускается при открытии BSL или вручную.

## Подготовка

Команда **Подготовить проектный и языковой компоненты** последовательно проверяет
project, форматтер и анализатор и предлагает установить отсутствующие инструменты.
Для первого project предлагается полный комплект ESKA с выбранной версией;
установка требует
нажатия кнопки. Автоматическая инициализация проекта не выполняется.

Начиная с ESKA 0.15.0 официальные релизы содержат компонентные ZIP и полный
комплект. Первая установка использует официальный shell/PowerShell installer:
`eska`, `eska-project`, `eska-check`, `eska-build`, `eska-vcs`, `eska-fmt` размещаются
в `~/.eska/bin`. Установщик обновляет пользовательский PATH; новые встроенные
терминалы получают каталог через `environmentVariableCollection`, даже если
редактор запущен со старым окружением. Уже открытый терминал нужно открыть заново.
Успех подтверждается версиями всех шести executable, receipt cargo-dist и
проверкой Metadata API project. Отсутствующая команда считается ошибкой установки.
Чужие или выборочно установленные компоненты не перезаписываются полным
установщиком. Существующая компонентная установка продолжает обновляться через
свои ZIP; для собственного бинарника можно задать абсолютный путь.
Analyzer 0.4.0 устанавливается из готового официального app asset.

Для первого запуска без сети задайте абсолютные пути в
`eska.explorer.executable` и `eska.explorer.analyzerExecutable`.
Повторное подключение с доступными компонентами не требует сети; фоновые
проверки можно выключить отдельно. Собственный offline-дистрибутив не создаётся.

Стандартные имена ищутся сначала в управляемом каталоге, затем в абсолютных
каталогах PATH. Относительные PATH entries пропускаются. Явный путь не имеет
fallback; пропавший или несовместимый бинарник не заменяется другой программой.
При ошибке анализа дерево продолжает работать.

## Два индикатора и обновления

`ESKA v…` показывает версию фактически подключённого project; `BSL Analyzer v…`
— проверенного выбранного бинарника. Отсутствие, ошибка, отключение и приостановка
видны в подписи. Предлагаемая версия не подменяет установленную. Подсказка
показывает компонент, выбранный путь, состояние, управляемый путь и доступный релиз.

Нажатие каждого индикатора проверяет свой компонент. Команды также доступны
в палитре: **Проверить обновления ESKA** и **Проверить обновления BSL Analyzer**.
`eska.explorer.checkForUpdates` управляет только ESKA;
`eska.explorer.checkForAnalyzerUpdates` — только анализатором. Для каждого
сохраняется отдельная отметка времени на workspace host, не чаще раза в сутки.
Ручная проверка не зависит от этого интервала и допускает отмену.

Проверки и установка имеют раздельные состояния занятости. Сбой, отмена или
выключенная проверка одного компонента не блокируют другой. После отдельного
согласия обновляется выбранный компонент и повторно проверяется его
фактическая версия. Непроверенная версия Analyzer показывается с ограничением;
произвольный `latest` не устанавливается. Пользовательские бинарники не
перезаписываются: предложение относится к управляемой установке. Используемый
компонент из другого пути не переключается и не перезапускается.

Исключение — полный комплект, установленный официальным cargo-dist installer
в `~/.eska/bin`. У него общий receipt `eska-receipt.json`, поэтому Explorer
проверяет владельца, каталог и состав комплекта и вызывает соседнюю
`eska update --target-version <version> --format json`. Предложение явно
указывает, что обновится весь комплект ESKA. Analyzer остаётся отдельным.
Установка показывается в терминале задачи; после неё проверяется Metadata API
нового `eska-project`, а используемое соединение восстанавливается, в том числе
при ошибке установщика. Пользовательский backend из другого пути сохраняется.
Проверка доступной версии допускает отмену; уже запущенный установщик не имеет
отдельной кнопки отмены в уведомлении. Ошибки видны в терминале задачи, общего
автоматического отката для cargo-dist нет.

Файлы cargo-dist не преобразуются в компонентную установку. Смешанный каталог
с компонентными receipts, незавершённой транзакцией или изменёнными после
подтверждения файлами блокирует обновление. Cargo и другие внешние установки
project автоматически не перезаписываются.

Если backend рассчитан на другую версию Analyzer, Explorer сообщает о
несовместимости и предлагает команду **Проверить обновления ESKA**. Это не
повреждение протокола; обновления одного Analyzer или расширения недостаточно.
Для пользовательского пути требуется обновить именно выбранную сборку project.

При конфликте со сторонним BSL-расширением собственный клиент имеет состояние
`suspended-conflict`. Проверка и установка обновлений доступны независимо;
завершение установки сохраняет текущую причину приостановки и не возобновляет
язык. [Правила конфликта](language-service.md#конфликт-расширений).

## Размещение и сохранность

Project использует общий каталог `~/.eska`: `bin/eska-project[.exe]`.
Первый полный комплект принадлежит официальному установщику и его receipt
cargo-dist. При выборочной установке project receipt находится в
`components/eska-project.json`, notices — в `share/eska/eska-project/`.
Форматы component ZIP, contract schema 2 и receipt совпадают с T97.
Python CLI и Explorer могут проверять, обновлять и удалять project, установленный
другим frontend. Остальные ESKA-компоненты сохраняются.

Analyzer размещается отдельно: `~/.eska/analyzer/bin/bsl-analyzer-app[.exe]`,
receipt и пять upstream license/NOTICE файлов в этом же частном namespace.
Предварительно устанавливать Python, Cargo, Git или CLI ESKA не требуется.
На Remote пути и выбор OS/CPU относятся к workspace extension host;
реальная приёмка Remote, Windows и macOS пока не выполнена.

Перед исполнением проверяются точные имя, origin, размер и SHA-256 GitHub asset.
ZIP допускает только объявленный executable и обычные license-файлы с проверенными
размерами и хешами. Проверяются config/bridge schemas и API project; у Analyzer —
реальные `--version` и `contract`. Готовый executable проверяется в staging
и после установки. Локальные dev builds project проверяются Metadata API,
без требования стабильного release-номера или установочного receipt.

Project-пакеты поддерживают существующие семь targets T97. Upstream app 0.4.0
опубликован только для Linux x64 GNU, Windows x64 и macOS ARM64. Другие targets
не подменяются соседней архитектурой; совместимый собственный бинарник можно
выбрать явно. Наличие asset не является приёмкой соответствующей ОС.

Общий exclusive claim `.eska-components.claim` координирует Explorer и обновлённый
Python CLI. Нельзя запускать параллельно старый CLI bundle без этого протокола.
До первой замены сохраняются backups и журнал; receipt публикуется последним.
Отмена и обработанная ошибка возвращают предыдущие байты. Файлы с изменившимся
хешем и чужие установки не перезаписываются.

При прерванной транзакции доступны команды **Восстановить установку
project-компонента** и **Восстановить установку Analyzer**. Проверяются все текущие
хеши, backups и границы записи до восстановления любого файла. Конфликт
с внешней правкой сохраняет backups. Оставшийся claim можно убрать только при
явном восстановлении после подтверждённого завершения PID владельца; живой,
повторно использованный PID и повреждённый claim сохраняются.
Потеря питания и сетевые FS не аттестованы; авария самого восстановления
может потребовать ручной проверки `.eska-components.recovering`.
